# Project Brain v1.2 并发一致性设计

## 目标

让多个 Codex 会话、多个 MCP 进程同时访问同一个工作区时，不再竞争 SQLite 写锁；每个分析请求只读取一份完整、可追溯的索引快照。

## 已确认的产品语义

- 默认 `stable`：立即读取最近一份完整快照；发现默认分支基线变化时，返回 `refreshing`，但不混用构建中的数据。
- `latest`：等待已合并的刷新任务完成，再读取新快照。
- 每个报告固定记录 `snapshot_id`、快照完成时间、仓库默认分支及 commit、`rule_revision`。
- 索引、协调状态、反馈和快照均只保存在用户本机；不写业务仓库。

## 现状与根因

当前每个 MCP 进程在工具调用中直接打开同一个 `index.sqlite`，并对除报告查询/反馈外的大部分请求执行 `indexer.Refresh`。刷新会持有仓库级写事务，因此两个 `project-brain mcp E:\BasisProject` 进程可同时争夺写锁，也可能使不同请求观察到不同刷新阶段。

## 方案选择

采用“每工作区唯一协调者 + 不可变索引快照”。

不采用仅设置 SQLite `busy_timeout` 的方案：它只能降低报错频率，无法提供完整快照和跨会话一致性。也不依赖 Codex 复用单一 MCP 进程：多会话时该前提不成立。

## 架构

```text
MCP/CLI 客户端
      │ 本地 IPC
      ▼
工作区协调者（唯一写入者）
 ├─ 刷新合并队列
 ├─ 快照选择器
 ├─ 报告/反馈版本选择器
 └─ 崩溃恢复与旧快照回收
      │
      ├─ control.sqlite     协调状态、反馈、报告、规则
      ├─ snapshot-001.sqlite 已完成，只读
      └─ snapshot-002.sqlite 构建中，对查询不可见
```

协调者是本机进程；每个工作区最多一个。MCP/CLI 变为薄客户端：连接已存在协调者，连接失败时仅一个进程取得工作区租约并启动它，其他客户端等待其就绪。SQLite 采用 WAL、`busy_timeout` 和短事务作为兜底，不再承担并发调度职责。

## 快照与原子切换

### 快照文件

- `snapshot-<id>.sqlite`：包含一份完整索引；已激活后永不修改。
- 构建从活跃快照复制到 staging 快照，在 staging 内完成基线变更的增量更新。
- staging 成功校验后，协调者在 `control.sqlite` 的单事务中更新 `active_snapshot_id`。
- 读请求在开始时选择 `snapshot_id` 并保持连接到该文件直至请求结束；切换不会影响进行中的请求。

### 保留与磁盘边界

- 默认保留活跃快照与上一份完整快照；无读者引用的更旧快照异步清理。
- 构建期间需要活跃快照、staging 快照和 WAL 空间。启动刷新前检查可用空间，低于“当前快照大小的两倍加 128 MiB”时拒绝刷新并保留旧快照。
- 首次从 v1.1 迁移时，将既有 `index.sqlite` 迁移为 `snapshot-001.sqlite`，不重新扫描业务仓库。

## 刷新合并与新鲜度

1. 客户端请求 `stable` 或 `latest`，协调者读取工作区默认分支 commit 指纹。
2. 指纹等于活跃快照基线：直接返回该快照。
3. 指纹不同且没有同目标刷新：创建一条刷新任务并构建 staging 快照。
4. 指纹不同且已有刷新：请求合并进现有任务，不产生第二个 `git archive` 或第二个写入者。
5. `stable` 立即返回活跃快照和 `refreshing` 状态；`latest` 等待任务，超时则返回活跃快照、`refreshing` 和明确的等待超时信息。

刷新状态为 `idle`、`refreshing`、`failed`、`recovering`。状态接口返回活跃快照、目标基线、刷新开始时间、已完成仓库数和失败原因。

## 反馈与报告一致性

- `control.sqlite` 保存报告、反馈、规则和单调递增的 `rule_revision`。
- 反馈写入由协调者串行执行；提交成功后才增加 `rule_revision`。
- 分析请求在开始时固定 `snapshot_id` 与 `rule_revision`，报告将两者持久化。
- 规则更新不会改写历史报告；复查历史报告默认返回原始 JSON。新分析使用新规则版本。

## 本地 IPC 与崩溃恢复

- 控制端点按工作区哈希存放，仅允许本机用户访问。
- 协调者状态文件含 PID、启动时间、协议版本和端点；启动方先探活，再通过工作区租约决定是否接管。
- 发现失联协调者时，新协调者删除未完成 staging 快照、保留最后活跃快照，并把状态记为 `recovering` 后恢复服务。
- staging 从不成为活跃快照，因此崩溃不会暴露半索引数据。

## 对外契约

现有 MCP 工具名保持兼容。所有读工具可接受可选参数：

```json
{"freshness":"stable|latest", "snapshot_id":"可选固定快照"}
```

响应新增：

```json
{
  "snapshot_id":"snapshot-002",
  "rule_revision":12,
  "freshness":"up_to_date|refreshing|stale",
  "active_baseline":"...",
  "refresh_target":"..."
}
```

`snapshot_id` 不存在或已回收时返回明确错误，不悄悄改用最新数据。`record_analysis_feedback` 返回写入后的 `rule_revision`。

## 验收

### 自动化

- 三个独立客户端同时请求 `latest`：断言仅创建一个刷新任务和一个写入者。
- 一个请求在 `snapshot-001` 查询，另一个完成切换至 `snapshot-002`：前者全程读取 `001`，后者读取 `002`。
- `stable` 不等待刷新；`latest` 等待并在超时时返回完整旧快照与状态。
- 反馈写入与分析并发：每份报告只出现一个固定 `rule_revision`。
- 强制终止协调者：staging 被恢复清理，最后活跃快照继续可查询。
- 迁移 v1.1 既有索引：文件数与查询结果保持可用。

### 真实工作区

在 `E:\BasisProject` 记录首次迁移、一次默认分支变化后的增量刷新、三个并发分析请求的耗时和磁盘占用；前后逐仓库对比 `git status --short`，证明零业务仓库写入。

## 非目标

- 不 fetch、不 checkout、不构建或测试业务仓库。
- 不实现跨电脑共享协调者或云端索引。
- 不改变现有静态关系提取规则；本版本只保证其并发与一致性语义。
